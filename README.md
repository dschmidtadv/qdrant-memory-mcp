# Qdrant Memory MCP

A local-first, long-term memory server for AI coding agents. It exposes two tools —
`memorize_context` and `recall_context` — over the Model Context Protocol (MCP), backed
by a [Qdrant](https://qdrant.tech/) vector database, so an agent can store architectural
decisions, notes, and project context in one session and retrieve them by meaning in a
later one.

## Why This Exists

AI coding agents lose context the moment a session ends. Re-explaining architectural
decisions, naming conventions, and "why we did it this way" at the start of every session
wastes tokens and invites regressions. Most hosted solutions to this problem (SaaS memory
layers, cloud-only RAG platforms) require sending your code, decisions, and internal
documentation to a third-party service.

Qdrant Memory MCP takes a local-first approach instead:

- **In local development** (`NODE_ENV=local`, the default), embeddings are generated by
  an **Ollama** container running on your own machine and stored in a **Qdrant** container
  on your own machine. No code or content you memorize needs to leave your workstation.
- **In production**, the same server can be pointed at **AWS Bedrock** for embeddings so
  it scales without running a GPU/CPU-bound model yourself — you opt into that trade-off
  explicitly via `NODE_ENV=production`, rather than having it be the only option.
- Content is scoped by `project`, so one Qdrant instance can hold isolated memory for
  multiple codebases without cross-contamination.

In short: a small, auditable, self-hosted alternative to routing an agent's working memory
through someone else's cloud.

> **Note on transports:** `TRANSPORT_MODE=stdio` (the default) is the fully implemented,
> production-usable path for local IDE integration. `TRANSPORT_MODE=http` exists for a

> (`mcp-server/src/transports/http-transport.ts`) returns a placeholder response rather
> than routing to the MCP server — treat HTTP transport as not yet production-ready.

## How It Works

1. **`memorize_context(content, project, tags?)`** splits `content` into ~1000-character
   chunks with 200-character overlap (`chunking.ts`), generates an embedding for each
   chunk in batches of 5 (`batching.ts`, to stay under embedding-provider rate limits),
   and upserts each chunk as a point in Qdrant with `project`, `tags`, `timestamp`, and
   the chunk text stored as payload.
2. **`recall_context(query, project, limit?, tags?)`** embeds the query text, searches
   Qdrant filtered by `project` (and `tags`, if given), and returns the top matches as
   Markdown with a cosine-similarity score per result. The response is sanitized and
   capped at 16KB to stay within MCP stdio transport limits.
3. `recall_context` retries up to 3 times with exponential backoff on transient failures
   (connection resets, timeouts, 5xx responses) and fails immediately on validation or
   4xx errors.
4. Every tool call emits Prometheus metrics (call counts, error counts, latency
   histograms, chunk counts, average recall score) via `metrics.ts`.

## Quick Start

### Prerequisites

- Docker Desktop (macOS/Windows) or Docker Engine (Linux)
- Node.js 20+
- Git

### 1. Clone and start the local stack

```bash
git clone https://github.com/dschmidtadv/qdrant-memory-mcp.git
cd qdrant-memory-mcp
docker-compose up -d
```

This starts four containers: `qdrant-local`, `ollama-local`, `prometheus`, and `grafana`.
Check they're healthy:

```bash
docker-compose ps
```

### 2. Build and start the MCP server (on the host)

```bash
cd mcp-server
npm install
npm run build   # compiles TypeScript to dist/
npm start
```

Expected output:

```
Connecting to Qdrant at: http://localhost:6333
Environment: local
Collection: agent-memory (768-dim)
Qdrant initialized successfully
Transport mode: stdio
MCP Server connected via stdio transport (local IDE mode)
Metrics server listening on :9091
```

### 3. Point your MCP client at it

Any MCP-compatible client (Claude Code, an IDE extension, a custom agent) can launch
`node dist/index.js` from `mcp-server/` as a stdio MCP server and will see the
`memorize_context` and `recall_context` tools.

### 4. Access dashboards

- Prometheus: http://localhost:9090
- Grafana: http://localhost:3002 (default login `admin` / `admin`)
- Raw MCP metrics: http://localhost:9091/metrics

## Installation

### System Requirements

**Local development**
- 4GB RAM minimum (8GB recommended — Qdrant alone is capped at 4GB in `docker-compose.yml`)
- ~10GB disk space (Qdrant index + Ollama model weights)
- Docker with at least 4 CPU cores available

**Production (if deploying the server itself to the cloud)**
- A container platform able to run the `mcp-server/Dockerfile` image
- A reachable Qdrant instance (self-hosted or Qdrant Cloud)
- AWS credentials with Bedrock access, if using `NODE_ENV=production`

### Step-by-step

```bash
# 1. Install server dependencies
cd mcp-server
npm install

# 2. Configure environment
cp .env.example .env   # create this from the "Configuration" table below if .env.example isn't present
nano .env

# 3. Build
npm run build

# 4. Pull the Docker images used by docker-compose.yml
docker pull qdrant/qdrant:latest
docker pull ollama/ollama:latest
docker pull prom/prometheus:latest
docker pull grafana/grafana:latest

# 5. Start the stack and the server
cd ..
docker-compose up -d
cd mcp-server && npm start
```

Qdrant auto-creates its collection (`agent-memory` locally, `agent-memory-prod` in
production) on first server start. Verify it exists:

```bash
curl http://localhost:6333/collections
```

> `mcp-server/.env.example` is not currently checked into the repo — use the variable
> table in [Configuration](#configuration) to create `mcp-server/.env` by hand.

## Configuration

All configuration is via environment variables, read in `mcp-server/src/*.ts` with
`dotenv`.

| Variable | Default | Purpose |
|---|---|---|
| `NODE_ENV` | `local` | `local` uses Ollama embeddings (768-dim) and the `agent-memory` collection; `production` uses AWS Bedrock (1024-dim) and `agent-memory-prod`. |
| `TRANSPORT_MODE` | `stdio` | `stdio` for local IDE integration (fully implemented); `http` for the in-progress cloud transport (currently a stub — see [Architecture](#architecture)). |
| `MCP_PORT` | `3000` | HTTP port, only used when `TRANSPORT_MODE=http`. |
| `QDRANT_URL` | `http://localhost:6333` | Qdrant REST endpoint. Use `http://qdrant-local:6333` from inside the Docker network. |
| `QDRANT_COLLECTION` | *(auto by `NODE_ENV`)* | Override the auto-selected collection name. |
| `OLLAMA_URL` | `http://localhost:11434` | Ollama endpoint used when `NODE_ENV=local`. |
| `OLLAMA_MODEL` | `nomic-embed-text:latest` | Embedding model pulled by Ollama. |
| `AWS_REGION` | `us-east-1` | Region for the Bedrock client, used when `NODE_ENV=production`. |
| `AWS_BEDROCK_MODEL` | `amazon.titan-embed-text-v2:0` | Bedrock embedding model, used when `NODE_ENV=production`. |
| `LOG_LEVEL` | `info` | Log verbosity. |

The MCP server listens for metrics on a fixed port, `9091`, regardless of transport mode.

### Docker Compose services

`docker-compose.yml` defines four services on a shared `qdrant-mcp-network` bridge
network: `qdrant-local` (port 6333, 4GB memory limit), `ollama-local` (port 11434),
`prometheus` (port 9090), and `grafana` (port 3002, mapped from the container's 3000).
Health is monitored externally by `scripts/mcp-monitor.sh` rather than Docker
healthchecks alone.

> **Linux note:** if you run the MCP server on the host (as in Quick Start) and want
> Prometheus (in Docker) to scrape it via `host.docker.internal`, native Linux Docker
> Engine needs `--add-host=host.docker.internal:host-gateway`; this isn't required on
> Docker Desktop for macOS/Windows.

## API Reference

### `memorize_context`

Stores content in the memory bank.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `content` | string | yes | Markdown/text content to store. |
| `project` | string | yes | Project identifier used to scope retrieval. |
| `tags` | string[] | no | Categorization tags. |

Returns a plain-text confirmation, e.g. `Successfully stored 3 chunks in memory for
project "qdrant-memory-mcp"`.

Emits: `mcp_chunks_stored_total`, `mcp_memorize_duration_seconds`,
`mcp_embedding_duration_seconds`.

### `recall_context`

Retrieves relevant content from the memory bank.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `query` | string | yes | Natural-language search query. |
| `project` | string | yes | Project identifier to filter by. |
| `limit` | integer | no (default 5) | Maximum results to return. |
| `tags` | string[] | no | Restrict results to these tags. |

Returns Markdown with one `## Result (Score: 0.xx)` section per match, including source,
tags, timestamp, and (truncated to 1000 characters) content. Retries up to 3 times on
transient errors before failing.

Emits: `mcp_tool_calls_total`, `mcp_recall_duration_seconds`, `mcp_recall_score_avg`.

### Metrics endpoint

`GET http://localhost:9091/metrics` (Prometheus text format):

```
# Counters
mcp_tool_calls_total          — total tool invocations, labeled by tool/project/status
mcp_tool_errors_total         — total tool errors, labeled by tool/error_type
mcp_chunks_stored_total       — chunks stored in Qdrant, labeled by project

# Histograms
mcp_recall_duration_seconds    — recall_context latency
mcp_memorize_duration_seconds  — memorize_context latency
mcp_embedding_duration_seconds — embedding generation time, labeled by provider

# Gauges
mcp_recall_score_avg — average cosine similarity of the latest recall, labeled by project
mcp_projects_active  — declared gauge for active project count
mcp_vectors_stored   — declared gauge for total vectors stored
```

## Monitoring

### Prometheus

URL: http://localhost:9090. Configured in `monitoring/prometheus/prometheus.yml` to
scrape Qdrant, the MCP server's metrics port, and itself.

Useful queries:

```promql
# MCP tool call rate
rate(mcp_tool_calls_total[5m])

# recall_context p99 latency
histogram_quantile(0.99, mcp_recall_duration_seconds_bucket)

# Tool error rate
rate(mcp_tool_errors_total[5m]) / rate(mcp_tool_calls_total[5m])
```

### Grafana

URL: http://localhost:3002 (`admin`/`admin`). Provisioned with the
`qdrant-mcp-overview` dashboard from `monitoring/grafana/dashboards/`.

### Alert rules

Defined in `monitoring/prometheus/alerts/qdrant-mcp.yml`:

| Alert | Condition |
|---|---|
| `QdrantDown` | Qdrant unreachable > 1 min |
| `MCPServerDown` | MCP server unreachable > 30s |
| `RecallLatencyHigh` | `recall_context` p99 > 500ms for 5 min |
| `EmbeddingLatencyHigh` | Embedding p99 > 200ms for 5 min |
| `ToolErrorRateHigh` | Tool error rate > 1% for 5 min |
| `QdrantMemoryHigh` | Qdrant memory > 90% for 10 min |
| `QdrantDiskHigh` | Qdrant disk > 80% for 30 min |
| `OllamaDown` | Ollama unreachable > 1 min |

Cloud monitoring (e.g. CloudWatch) is not yet implemented in this repository.

## Deployment

### Local development

```bash
docker-compose up -d
cd mcp-server && npm run build && npm start
```

### Toward production (AWS)

The intended production shape is:

- **ECS Fargate** running the image built from `mcp-server/Dockerfile`
- **Qdrant** reachable from that task (self-hosted on EFS-backed storage, or Qdrant Cloud)
- **AWS Bedrock Titan v2** for embeddings (`NODE_ENV=production`), avoiding a local
  Ollama sidecar

```bash
NODE_ENV=production
TRANSPORT_MODE=http
QDRANT_URL=http://<your-qdrant-endpoint>:6333
AWS_REGION=us-east-1
AWS_BEDROCK_MODEL=amazon.titan-embed-text-v2:0
MCP_PORT=3000
```

```bash
docker build -t qdrant-memory-mcp:latest ./mcp-server
docker tag qdrant-memory-mcp:latest <account>.dkr.ecr.<region>.amazonaws.com/qdrant-memory-mcp:latest
docker push <account>.dkr.ecr.<region>.amazonaws.com/qdrant-memory-mcp:latest
```

> As noted above, `TRANSPORT_MODE=http` currently serves a placeholder response from
> `/mcp` rather than real MCP routing. Implementing a working HTTP transport is a
> prerequisite before this path is usable in production — see
> `mcp-server/src/transports/http-transport.ts`.

## Optional: Editor/Agent Rules

The `agent/` directory and `CLAUDE.md`/`AGENTS.md` at the repo root contain rule and
skill configuration for AI coding assistants (Claude Code, Roo Code) that are used to
*develop this repository itself* — things like coding conventions and skill definitions
for those tools. They are not part of the MCP server's runtime and are not required to
build, run, or consume `memorize_context`/`recall_context`. `make install-modes` (see
`Makefile`) symlinks `agent/rules-*/` into a local Roo Code configuration directory for
contributors who use that editor; it has no effect on the server itself.
