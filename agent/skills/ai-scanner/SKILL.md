# AI Scanner

## What this does

Runs a block of text through up to four independent detectors via the `hf-scanner` MCP server's `scan_text_with_huggingface` tool, and reports each verdict separately:

- `openai-community/roberta-base-openai-detector` (hosted, **Real**/**Fake**) — RoBERTa classifier trained on GPT-2 output
- `Hello-SimpleAI/chatgpt-detector-roberta` (hosted, **Human**/**ChatGPT**) — RoBERTa classifier trained on the HC3 corpus of real ChatGPT output
- **Fast-DetectGPT** (local, no API call, no token needed) — a zero-shot conditional-probability-curvature detector run on-device with GPT-2, architecturally unrelated to the two RoBERTa classifiers above
- **Sapling** (hosted, commercial, optional — needs `SAPLING_API_KEY`; skipped cleanly if not set) — a closed-source API that catches this tool's corporate-jargon blind spot, but has its own confirmed severe false-positive bias on formal human writing

**This is still not a reliable detector, and no signal added so far has closed the gap without opening a new one.** On one specific test paragraph, both hosted RoBERTa models agreed on "Human" for text deliberately written to sound AI-generated, while Fast-DetectGPT (a different mechanism) correctly leaned "AI." **That result did not generalize.** Tested against six realistic AI-generated corporate-jargon passages, Fast-DetectGPT agreed with the hosted classifiers' wrong "Human" verdict on 5 of 6. Sapling correctly caught all 6 of those — but when tested against genuinely human **formal** writing (cover letters, academic prose, meeting minutes, etc.), it confidently misclassified 5 of 6 as AI. **Every signal in this tool has a confirmed, serious blind spot somewhere; none of them is safe to trust alone, and none of the combinations tested so far reliably fixes the others.** Treat every result as a rough hint, not a verdict. The local detector's own AI/Human/Ambiguous label is uncalibrated (its raw curvature number is the real signal), and Sapling's "AI" verdict specifically should be treated with high suspicion on anything formal or professional — the tool's own output appends an explicit warning in that case.

## Instructions

1. Confirm the `hf-scanner` MCP server is connected (Zoo Code MCP Servers panel). If it's not listed or shows disconnected, tell the user to check that:
   - `/Users/dietrichgottfriedschmidt/apps/ai-text-scanner/.env` has a valid `HF_API_TOKEN` (only needed for the two hosted RoBERTa detectors — the local one works without it). `SAPLING_API_KEY` is optional; the tool skips that signal cleanly if it's not set.
   - The `hf-scanner` entry in `mcp_settings.json` is not `disabled`.
2. Call the `scan_text_with_huggingface` tool with the full text to scan as `text_to_scan`. Do not truncate or summarize the text before sending it — every detector needs the original wording. The first call in a session may take a moment longer while the local GPT-2 model loads (cached after that).
3. Report the result back plainly, and always lead with the unreliability caveat before the verdicts, not after: each detector's verdict, whether they agree, and a clear statement that this is a low-confidence hint that has been directly observed to be wrong even when detectors agree with each other. Never let the user walk away thinking a same-architecture "both agree" result is trustworthy — but note that agreement spanning the local detector too (a different mechanism) is a somewhat stronger, still-not-reliable signal. If Sapling reports "AI" and the text reads as formal or professional (business, legal, academic, technical), relay the tool's own inline warning about Sapling's confirmed bias in that direction rather than letting the user take the "AI" verdict at face value.
4. If a detector returns an error (e.g. cold-start "still loading" for a hosted detector, missing token, network failure, or a local inference error), relay that detector's error directly. A per-detector 503/cold-start error is safe to retry once after a few seconds for that detector only; other errors should be surfaced to the user as-is.
5. Do not use this tool's output to support any consequential judgment (academic integrity, hiring, discipline, etc.) even if asked to. If the user wants to use it that way, say plainly that every signal in this tool has a confirmed blind spot somewhere — the RoBERTa/Fast-DetectGPT combination misses fluent AI-generated corporate/business writing (5 of 6 test samples), and Sapling confidently misflags genuinely human formal/professional writing as AI (5 of 6 test samples) — and that no combination tested so far closes both gaps at once (see Notes).
6. If the user asks specifically about corporate/business-style text (jargon-heavy, buzzword-dense prose), proactively mention the confirmed blind spot before they rely on the result — a "Human" verdict from the RoBERTa/Fast-DetectGPT trio on this kind of writing is currently one of the least trustworthy results this tool produces. Conversely, if the text is formal/professional and Sapling calls it "AI," that specific verdict is also one of the least trustworthy results — mention both directions, don't just default to distrusting "Human."

## Notes

- Source project: [`~/apps/ai-text-scanner`](/Users/dietrichgottfriedschmidt/apps/ai-text-scanner) (originally built against GPTZero as `gptzero-mcp-server`, rewritten to use Hugging Face's free tier, upgraded to a two-model ensemble, downgraded in framing once testing showed the ensemble wasn't actually reliable, extended with a local Fast-DetectGPT signal, then that signal's actual benefit was tested against realistic samples and found not to generalize).
- **Corporate-jargon blind spot, confirmed and investigated**: a set of six AI-generated corporate/business passages (from `.ai-memory/AI_GENERATED_SAMPLES_ANALYSIS.md` in the source project) found the hosted GPT-2 classifier alone misclassified 5/6 as human, with the highest confidence (99.88–99.98%) on the heaviest-jargon samples. Adding Fast-DetectGPT did not fix this — it agreed with the wrong verdict on the same 5/6. Swapping in larger local scoring models (`gpt2-medium` 355M, `gpt2-large` 774M) instead of base `gpt2` (124M) did not consistently improve results either; some samples moved to a more confidently wrong verdict with the larger model, for a much higher model-load cost (60–108s vs ~1s). This looks like a genuine limitation of GPT-2-family models on this specific genre of prose, not something fixable by scaling within that family.
- **A pasted "deep research" report proposing further improvements contained fabricated or unverifiable specifics** (a wrong Sapling free-tier quota, an unsourced "downscaled Binoculars, ρ=0.84" claim with no findable citation) alongside real, verifiable content (Fast-DetectGPT itself, SENTRA, EchoPrompt are all real papers). Fast-DetectGPT was independently re-verified against its actual GitHub repo and ICLR paper before being implemented — the report's specific compute-requirement claims for it were not used; the implementation here was built directly from the paper's own Algorithm 1 and tested locally. Full-scale Binoculars remains researched-and-ruled-out for the reasons in the README (needs two 7B models, not servable via HF's free hosted-inference API).
- Most other free, HF-hosted "AI detector" models checked during development either aren't servable via HF's free Inference Providers router or fail to load; the two RoBERTa models wired up here were the only ones confirmed working against the live API — "working" here means "returns a response," not "is accurate."
- Lesson for future research requests on this project: verify specific numbers (quotas, benchmark scores, hardware requirements) against primary sources before treating them as fact, even when the surrounding paper/method names are real. A report can get the real citations right and still fabricate the details layered on top.
- **A commercial detector (Sapling) was manually tested first with a free-tier web check, then integrated as a fourth signal once an API key was available — and its full picture only emerged in two stages.** Stage 1 (manual, AI samples only): correctly flagged all 6/6 corporate-jargon samples this tool's other three signals miss (100% each) — looked like a clean win. Stage 2 (programmatic, once a real API key existed, tested against genuinely human FORMAL writing): 5 of 6 samples (cover letter, academic writing, news style, meeting minutes, legal clause, encyclopedic entry) were confidently misclassified as AI, several near 100%. **This is the identical disqualifying bias found in the rejected ModernBERT classifier below — confirmed in a second, independently-built system.** Sapling was kept as a signal (real value on the corporate-jargon axis) but the tool's own output now appends an explicit warning whenever Sapling says "AI." If a user asks "would a commercial tool do better," relay the full two-stage story, not just the encouraging Stage 1 result — the complete picture only appeared after specifically testing the failure mode the ModernBERT investigation had already flagged as a risk.
- **Investigated whether an open, self-hosted classifier could close the gap instead — rejected after thorough testing.** `GeorgeDrayson/modernbert-ai-detection-raid-mage` (Apache 2.0, trained on RAID + MAGE covering 38 generators) initially looked strong: caught 4/5 of the corporate-jargon samples this tool's ensemble misses. Broader testing against 8 samples of genuinely human formal writing (business email, academic prose, legal clause, cover letter, scientific abstract, meeting minutes, encyclopedic entry, news style) found **all 8 confidently misclassified as AI-generated, every one above 95% confidence** — this model appears to treat "formal writing style" as a proxy for "AI-generated" almost regardless of actual authorship. Since this tool's plausible use cases include checking real professional/academic writing, this is a disqualifying bias, not a minor caveat — it trades one confident-wrong-answer direction for another, arguably worse one. **Not integrated.** If a user asks about self-hosting a better model, relay this finding rather than suggesting this specific model as a fix.
- **Two more commercial platforms were checked (Winston AI, Pangram Labs) — neither was integrated.** Winston AI's default/latest model (`v4.18`) was found to return an identical `score: 0` regardless of actual input content (a real defect, reported to Winston); falling back to their older `v3.0` model correctly caught AI samples but still confidently misclassified a genuine human cover letter as AI — the same bias as everything else. Pangram Labs markets itself specifically as solving this exact problem (cites a real third-party COLING 2025 benchmark placement) and was tested manually via their free consumer web app (no free tier exists for their Developer API). **It failed too, and this was verified carefully**: short samples (~60-75 words) triggered a "Confidence limited — short text" caveat alongside a 100% AI verdict, so that result wasn't trusted; even 120 words (above Pangram's own documented 50-word minimum) still triggered the warning; only at 221 words did the warning clear, and the result held — **100% AI, no confidence caveat, on a genuinely human-written cover letter.** A controlled comparison of that exact 221-word text across every system tested (both hosted RoBERTa classifiers, Fast-DetectGPT, Sapling, ModernBERT, both Winston versions, Pangram) found that **only the two original RoBERTa classifiers got it right** — every other signal, free or paid, called it AI. **Four separately-built systems (ModernBERT, Sapling, Winston v3.0, Pangram) now confirm the same formal-writing-reads-as-AI bias**, including the one vendor whose own marketing most explicitly claimed to have solved it. This looks like a structural property of how these detectors get trained, not a flaw unique to one vendor — and strong grounds to distrust any vendor's accuracy marketing on this specific axis until independently tested.

## Rewriting AI-assisted drafts to sound more natural

This is a separate workflow from scanning, done directly by the agent (no MCP tool call, no external API) — the goal is helping the user sound like themselves, not evading detection.

1. Trigger: the user asks to make a draft "sound more natural," "less AI," "in my own voice," or similar, and hasn't provided writing samples or a style description to match.
2. Rewrite the text directly, targeting generic de-AI-ified prose:
   - Vary sentence length; break up uniform, list-like sentence structures.
   - Cut hedging and filler phrases ("it's important to note," "in today's fast-paced world," "as an AI language model").
   - Reduce repetitive structural tics (e.g. every paragraph ending in a triplet, overuse of em dashes or colons — see the org-wide punctuation guidance already in effect).
   - Keep the actual content, facts, and claims unchanged. This is a style pass, not a content rewrite — don't add, remove, or alter substantive claims.
3. If the user wants the rewrite to match a specific personal voice (not just generically "more natural"), ask for either a short style description or a couple of their own writing samples to anchor to — this skill doesn't store or infer a voice profile on its own.
4. Optional: after rewriting, offer to run the result through the scan workflow above so the user can see whether the rewrite actually reads as less AI-flagged. Treat that scan result with the same disagreement/inconclusive caveats as any other scan — it's a signal, not proof the rewrite "worked."
